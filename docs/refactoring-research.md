# Talaria refactoring priorities

Implementation: [changes and validation](/Users/yn/work/talaria/.worktrees/refactoring-research/docs/refactoring-implementation.md). This document preserves the original assessment; its source line references describe the baseline revision and may have moved during the refactor.

The highest return comes from making ownership explicit and making work proportional to what changed: one owner per chat, updates to the affected transcript rows, bounded history queries, and one consistent Hermes session lifecycle. Build and test boundaries should support those changes.

This assessment applies to fetched main commit **184c74224da178b27571fb226e0232c069ea046c**, on branch **refactoring-research**. It covers first-party native code, the bundled Python runtime, persistence, build rules, existing tests, and project specifications. Vendor libraries are excluded from size measurements. The production Source tree contains 45,827 physical lines; AgentRuntime contains 2,063; Tests contains 19,902. These counts locate concentrations of responsibility, rather than establish quality by themselves.

Code paths and algorithmic work below are verified from this revision. Expected latency and memory improvements remain hypotheses until measured in the desktop app. The session race was reproduced with a deterministic fake RPC transport, not a live Hermes installation.

| Rank | Proposal | Main benefit | Effort and risk |
| --- | --- | --- | --- |
| 1 | Give each chat a controller and unify tab lifecycle | Clear ownership, safer concurrent chats, easier feature additions | Large overall; moderate risk when extracted in stages |
| 2 | Make transcript rendering and reconciliation incremental | Remove quadratic scans, preserve message/view identity, reduce repeated work | Medium initial change; larger if virtualization is justified |
| 3 | Introduce asynchronous, query-oriented repositories | Eliminate full-history work on routine UI events and summary refreshes | Medium; search and attachment semantics need care |
| 4 | Separate Hermes transport from session coordination | Remove copied protocol code and enforce consistent lifecycle exclusion | Medium to large; cancellation and approval behavior are sensitive |
| 5 | Align build and test targets with module boundaries | Faster iteration and independent validation of the first four | Small dependency fix, followed by medium modularization |

Effort labels are planning judgments, not measured estimates. Each proposal can deliver useful improvements before its entire migration is complete.

**1. Give each chat a controller and unify tab lifecycle**

TalariaWindowController contains 6,936 lines and 404 implementation methods. More significant than its size is how it reaches chat state: 30 getter/setter pairs forward through a mutable currentChatPresentation. Background work uses withChatPresentation:perform: to save the focused presentation, substitute another one, run a block, and restore the original. There are 21 call sites. The existing scoped helper deliberately protects synchronous operations; its presence does not itself prove a current race. It does require every new asynchronous callback to understand which apparently window-local properties actually refer to a chat. [Property forwarding and scope helper](/Users/yn/work/talaria/.worktrees/refactoring-research/Source/TalariaWindowController.m:283)

A concrete path runs from an assistant update, through lookup of the originating chat presentation, through the scope helper, into render scheduling and control updates. Queued prompt actions and theme changes use the same mechanism. TLChatPresentation already owns messages, view caches, composer references, queue state, and find behavior, making it a practical extraction point. [Turn callbacks](/Users/yn/work/talaria/.worktrees/refactoring-research/Source/TalariaWindowController.m:3099), [presentation state](/Users/yn/work/talaria/.worktrees/refactoring-research/Source/TLChatPresentation.h:14)

The feature lifecycle is also only partly consolidated. TLFeatureTabController already provides a view owner, palette application, and close. TLWorkspaceTabRuntime can own that controller. The window still hardcodes particular controller kinds and has a separate chat cleanup path; downloads, history, and settings repeat activation/closure bookkeeping. [Existing lifecycle](/Users/yn/work/talaria/.worktrees/refactoring-research/Source/TLFeatureTabController.h:6), [runtime binding and disposal](/Users/yn/work/talaria/.worktrees/refactoring-research/Source/TalariaWindowController.m:5602), [downloads lifecycle](/Users/yn/work/talaria/.worktrees/refactoring-research/Source/TalariaWindowController.m:2162)

The proposed abstraction is a **TLChatTabController** that owns one presentation, transcript renderer, composer interaction, and local view lifecycle. Send, stop, and approval actions go to an injected conversation service. Stream callbacks address their originating controller directly. TalariaWindowController retains window chrome, split hosting, focus routing, and global dialogs.

Separate the lifetime of conversation work from the lifetime of its view. Closing a chat with queued work currently pauses and retains its presentation; replacing this with unconditional disposal would be a regression. A conversation runtime should explicitly own its queue and active runner, while a tab controller attaches or detaches the UI according to existing policy. [Queue-aware cleanup](/Users/yn/work/talaria/.worktrees/refactoring-research/Source/TalariaWindowController.m:5612)

Use the existing tab-kind enum with a small factory and lifecycle contract. Each runtime owns its feature controller and supplies activation, visibility, palette, and disposal behavior. Keep session persistence and validation in their existing state/store layer. The benefit is that a new tab feature needs a controller and factory entry, instead of changes across many window lifecycle methods.

One useful duplicate removal belongs in this extraction: main chat and quick input already share TLMessageInput, TLInputSuggestions, and TLInputSuggestionListView, but repeat keyboard navigation and completion policy. Their all-disabled navigation branches differ: main clears selection and returns NO; quick input returns YES after searching unsuccessfully. That difference needs an explicit behavioral contract, not an assumption that the surfaces must behave identically. Move wrap/skip-disabled selection into the existing list or a small selection model, and share typed completion/submit decisions while keeping surface-specific dismissal and queue behavior in adapters. [Main selection](/Users/yn/work/talaria/.worktrees/refactoring-research/Source/TalariaWindowController.m:3329), [quick-input selection](/Users/yn/work/talaria/.worktrees/refactoring-research/Source/TLQuickInputWindowController.m:448)

Deliver this in stages: first extract transcript/composer ownership with forwarding adapters; then route callbacks directly; then remove obsolete property proxies; finally consolidate feature construction and lifecycle. Avoid a giant base controller containing all feature policy.

Success means background streaming no longer substitutes the window's current presentation; one owner handles each tab's palette and disposal; and chat behavior can be tested without constructing the complete window. Reuse concurrent stream tests, SplitWorkspaceTests, WorkspaceRestoreTests, QuickInputTests, and TabShortcutTests. Cover two split chats with interleaved output, queued work, approval, draft promotion, theme switching, closing/reopening, and late callbacks. [Concurrent chat coverage](/Users/yn/work/talaria/.worktrees/refactoring-research/Tests/FeatureControllerTests.m:988), [split-focus/background-update coverage](/Users/yn/work/talaria/.worktrees/refactoring-research/Tests/SplitWorkspaceTests.m:253)

**2. Make transcript rendering and reconciliation incremental**

The existing renderer already makes useful optimizations: native layout updates are coalesced at 40 ms, WebKit content updates at 60 ms, unchanged text is suppressed, and rows/web views are cached. Preserve these mechanisms. The remaining problem is that a render still performs work across the full transcript even when one assistant message changed. [Native scheduling](/Users/yn/work/talaria/.worktrees/refactoring-research/Source/TalariaWindowController.m:4653), [Markdown update suppression](/Users/yn/work/talaria/.worktrees/refactoring-research/Source/MarkdownRenderer.m:114), [DOM scheduling](/Users/yn/work/talaria/.worktrees/refactoring-research/Source/MarkdownRenderer.m:206)

Two loops call indexOfObjectIdenticalTo: on the full message array for each previous or cached message. With n unchanged messages, these membership checks are quadratic. Rendering then visits every message, recomputes its signature, checks placement, and scans stack constraints to find its width constraint. Cached rows prevent rebuilding every WebKit document, but they do not eliminate this traversal. [Identity scans](/Users/yn/work/talaria/.worktrees/refactoring-research/Source/TalariaWindowController.m:4675), [every-row render](/Users/yn/work/talaria/.worktrees/refactoring-research/Source/TalariaWindowController.m:4734), [constraint lookup](/Users/yn/work/talaria/.worktrees/refactoring-research/Source/TalariaWindowController.m:4590)

Identity is also unstable at the persistence boundary. cacheHermesSession loads the existing transcript, deletes all its rows, matches attachment metadata by role/content, and inserts the incoming transcript afresh. For each incoming message it copies the remaining old-message array. Even an unchanged ordered transcript can copy n(n+1)/2 references; unchanged database message IDs are replaced as well. The UI compensates by transferring cached views between objects at matching positions. [Transcript replacement](/Users/yn/work/talaria/.worktrees/refactoring-research/Source/Database.m:280), [view transfer workaround](/Users/yn/work/talaria/.worktrees/refactoring-research/Source/TalariaWindowController.m:4673)

Use an explicit **transcript identity and change-set model**. First replace repeated identity searches with a pointer-identity set and retain row constraint handles. This is a small improvement that preserves current behavior. Next have updates identify the changed message and change kind: content, activities, approval, insertion/removal, or layout/palette. Reconcile only that row and any neighbor whose outgoing tail or spacing changed. Ordinary content deltas should not scan unrelated history.

Extract persistence reconciliation into a pure helper. Initially preserve the current role/content occurrence-matching policy using ordered buckets instead of repeated array copies. Then detect unchanged transcripts and preserve unchanged rows, applying inserts, updates, and removals transactionally. Preserve Talaria-owned attachments and reasoning fallback. Do not assume Hermes supplies stable upstream message IDs: the current adapter does not expose them. Inspect the installed gateway's supported response before adding an external identity key. A content hash alone is insufficient because identical messages are valid. [Current imported fields](/Users/yn/work/talaria/.worktrees/refactoring-research/AgentRuntime/hermes_gateway.py:327), [attachment and rollback tests](/Users/yn/work/talaria/.worktrees/refactoring-research/Tests/PromptBuilderTests.m:411)

There is a second, measurable follow-up opportunity for long messages: each changed Markdown render constructs a parser and replaces the complete content DOM before code/math enhancement. Cache the configured parser per document first. Profile before implementing block-level DOM updates; Markdown fences, lists, reference links, math, selection, and search make naive append-only rendering incorrect. [Markdown rendering function](/Users/yn/work/talaria/.worktrees/refactoring-research/Source/MarkdownRenderer.m:412)

Long histories also retain a WebKit-backed view for each rendered Markdown message. If memory profiling confirms this is material, add viewport-driven row reuse with a bounded cache, while keeping transcript search independent of which rows are currently mounted. AppKit collection items support reuse, but adopting that capability does not itself establish a performance gain for Talaria. [Web view creation](/Users/yn/work/talaria/.worktrees/refactoring-research/Source/MarkdownRenderer.m:124), [current search over mounted views](/Users/yn/work/talaria/.worktrees/refactoring-research/Source/TLChatPresentation.m:119), [Apple collection-view documentation](https://developer.apple.com/documentation/appkit/nscollectionview)

Success criteria should include operation counts as well as timings: no full-list membership scan for a content delta; unchanged transcript refresh produces no message writes; unchanged views retain identity; and visible text, attachments, approvals, code, tables, math, and search remain correct. Benchmark 100-, 1,000-, and 10,000-message fixtures plus a long streamed answer. Record native/DOM update duration, layout counts, allocations, and retained web views. Treat those as proposed measurements, not results already obtained.

The highest-risk cases are duplicate identical messages with different attachments, edited/reordered remote history, draft-to-persisted identity promotion, and preserving scroll/selection across a change. Existing rendered Markdown and chat-find tests are valuable regression coverage; add duplicate-occurrence and unchanged-write assertions at the reconciler boundary.

**3. Introduce asynchronous, query-oriented repositories**

TLDatabase's 1,245 lines span settings, credentials, agents, chats, messages, bookmarks, and browser history. The actionable issue is the shape of its API: callers often synchronously request entire collections or detailed records for summary-only UI work.

On browser navigation, title changes, and favicon arrival, the browser controller invokes historyChangedHandler. The window wires that directly to reloadHistoryPanel, which synchronously reads the complete browser history including favicon BLOBs, then reloads its table. Normal startup creates the history controller even while its tab is hidden, so the nil guard does not avoid this background work. [Browser event callbacks](/Users/yn/work/talaria/.worktrees/refactoring-research/Source/TLBrowserTabController.m:335), [window wiring](/Users/yn/work/talaria/.worktrees/refactoring-research/Source/TalariaWindowController.m:2376), [reload](/Users/yn/work/talaria/.worktrees/refactoring-research/Source/TalariaWindowController.m:6794), [startup construction](/Users/yn/work/talaria/.worktrees/refactoring-research/Source/TalariaWindowController.m:951)

Every history-search edit creates search strings, filters all entries, and sorts the combined chat/browser results. Remote history refresh also loops over all Hermes session summaries, calling cacheHermesSession for each one. Although messages:nil skips transcript writes, that method still calls loadChatWithID and hydrates every stored message before returning. This work reaches the main queue through native completion dispatch. [Search/filter work](/Users/yn/work/talaria/.worktrees/refactoring-research/Source/TLHistoryPanelController.m:126), [session-summary loop](/Users/yn/work/talaria/.worktrees/refactoring-research/Source/TalariaWindowController.m:6774), [unnecessary detailed return](/Users/yn/work/talaria/.worktrees/refactoring-research/Source/Database.m:320), [main-queue completion](/Users/yn/work/talaria/.worktrees/refactoring-research/Source/AgentClient.m:229)

Introduce narrow **ChatSummaryRepository, TranscriptRepository, and BrowserHistoryRepository** interfaces backed by one explicitly owned serial SQLite executor. Keep TLDatabase as a temporary facade. Use immutable results returned to the main queue, and carry request generations/agent identities so stale results cannot update a different view. Move all access to a connection under its owner; merely dispatching selected callers onto arbitrary background queues would create inconsistent ordering.

Separate batched upsertSessionSummaries from transcript reconciliation. A remote list refresh should write summaries in one transaction and return summaries without reading messages. Browser visit writes should publish inserted/updated/deleted IDs. While History is hidden, mark it dirty; when visible, coalesce relevant changes or update the affected page.

Bound reads with cursor pagination and lazy icon loading. There is already a browser_history_recent index on visited_at DESC, id DESC; use it rather than adding a duplicate. A schema-matching synthetic SQLite query-plan check found full scans for transcript lookup and prior-favicon lookup. Candidate indexes on messages(chat_id, id) and browser_history(url, id DESC) filtered to non-null favicons changed these to indexed SEARCH plans in that fixture. This is access-path evidence, not a desktop latency benchmark. Validate on the bundled SQLite and representative data before migrating. [Existing recent index](/Users/yn/work/talaria/.worktrees/refactoring-research/Source/DatabaseMigrator.m:285), [message query](/Users/yn/work/talaria/.worktrees/refactoring-research/Source/Database.m:958), [favicon lookup](/Users/yn/work/talaria/.worktrees/refactoring-research/Source/Database.m:328)

Do not weaken search to the currently loaded page. Search the full dataset, then page matching results. Current matching is case- and diacritic-insensitive and includes decoded URL text; plain SQLite LIKE is not an equivalent replacement. Preserve that contract with deliberate normalization or an equivalent search implementation. Preserve page-specific favicons, same-origin fallback, UTC ordering, and stable tie ordering. SQLite can use appropriate indexes for searching and ordering; EXPLAIN QUERY PLAN should verify the intended access path. [Current icon fallback](/Users/yn/work/talaria/.worktrees/refactoring-research/Source/Database.m:362), [SQLite query planning](https://www.sqlite.org/queryplanner.html), [EXPLAIN QUERY PLAN](https://sqlite.org/eqp.html)

Implement summary-only imports first, then database queue ownership, then visibility-aware history updates and pagination. Schema normalization of favicons can wait until measurement justifies it. Keep settings/Keychain compensation and supported migration compatibility intact while moving persistence boundaries.

Success means a normal navigation does not materialize the full history while hidden; a visible refresh reads a bounded page; summary refresh performs no message SELECTs; and switching filters/agents cannot publish stale results. Use BrowserHistoryTests and bookmark/migration fixtures, plus statement-count and bounded-row assertions with 100,000 synthetic visits. Measure event-loop stalls and allocated bytes before claiming speedups.

**4. Separate Hermes transport from session coordination**

The host/guest boundary repeats substantial plumbing. Six AgentClient wrappers—providers, automations, credentials, skills, history, and commands—generate IDs, accumulate text, reparse JSON, validate a dictionary, and dispatch completion. Python serializes structured results into strings inside content deltas, so native code decodes the outer JSON and then parses the inner string again. Only the skills accumulator explicitly filters content-kind deltas. [Repeated wrappers](/Users/yn/work/talaria/.worktrees/refactoring-research/Source/AgentClient.m:261), [guest result encoding](/Users/yn/work/talaria/.worktrees/refactoring-research/AgentRuntime/talaria_agent.py:249)

At the same time, HermesGateway coordinates process calls, persistent-to-live session mappings, sessions, listeners, approvals, and lock tables. Session lifecycle operations do not all use the same exclusion rule: model selection takes a session lock, while history deletion checks active listeners without taking that lock. A model switch can therefore be in flight before there is a listener to block deletion. [Model-change locking](/Users/yn/work/talaria/.worktrees/refactoring-research/AgentRuntime/hermes_gateway.py:511), [deletion](/Users/yn/work/talaria/.worktrees/refactoring-research/AgentRuntime/hermes_gateway.py:332)

A deterministic probe paused the actual select_model method inside a fake config.set call, then called the actual delete_history_session method. Deletion succeeded while the model switch owned the session lock; after release, the switch returned the now-removed live session. The recorded RPC order was config.set → session.close → session.delete → session.status. This demonstrates inconsistent lifecycle exclusion; live Hermes may instead return an error depending on timing. The portable [probe](/Users/yn/work/talaria/.worktrees/refactoring-research/docs/research/session-lifecycle-probe.py) uses temporary files and fake RPC only.

Create a **thin transport plus session owner**. Transport owns framing, correlation, structured result/delta/error parsing, cancellation delivery/socket lifecycle, and exactly-once completion. The session owner controls interrupt/drain semantics. A shared JSON-operation executor replaces the six accumulators while public domain methods keep their own schema validation. A SessionRegistry resolves persistent identities and chat aliases to one SessionController that owns lifecycle state and the session gate.

Creation/resume, history open/delete, model changes, turn submission, approval continuation, and stop/drain must coordinate through that owner. Interrupt must remain deliverable while a turn owns its gate; the gate stays held until terminal-event draining completes. Queuing Stop behind the running turn would deadlock cancellation. Provider configuration remains an explicit runtime-wide operation. Preserve the transport reader's ability to receive responses while an operation waits; holding its routing lock across a blocking RPC would introduce deadlocks. Preserve warm process reuse and isolated supporting-model sessions. [Gateway state](/Users/yn/work/talaria/.worktrees/refactoring-research/AgentRuntime/hermes_gateway.py:66), [support-session isolation](/Users/yn/work/talaria/.worktrees/refactoring-research/AgentRuntime/hermes_gateway.py:419)

These should be separate reviewable changes. First normalize the existing host accumulator implementation without changing wire format. Independently add the lifecycle exclusion regression and route conflicting operations through a consistent session gate. Then introduce structured result events and typed tool/approval payloads, coordinating bundled host and guest compatibility. Extract the session record/state machine after behavior is covered, keeping the existing gateway facade for callers.

This improves extensibility by making a new Hermes feature add a domain operation rather than another parser/lifecycle variant. Removing nested JSON also avoids some serialization work, but no end-to-end speedup has been measured. The concrete payoff is consistent contracts and session correctness.

Validation should consume shared NDJSON fixtures from native and Python code: arbitrary byte/Unicode boundaries, multiple frames per read, wrong IDs, malformed payloads, EOF before completion, cancellation during connect, and exactly-once terminal delivery. Add deterministic barriers for delete-versus-model-change, delete-versus-preparation, approval interruption, and process death. Retain existing stop/drain, cross-chat, approval identity, discovery, and no-HTTP tests. [Cancellation and gateway tests](/Users/yn/work/talaria/.worktrees/refactoring-research/Tests/test_hermes_gateway.py:221), [guest disconnect tests](/Users/yn/work/talaria/.worktrees/refactoring-research/Tests/AgentRuntimeTests.py:113)

**5. Align build and test targets with module boundaries**

Every app object rule depends on the entire APP_HEADERS set. Consequently, editing any app header makes every app object out of date, even when it does not import that header. This is an explicit dependency-graph fact, not a measured build-time claim. At least 15 native test targets in the main Makefile link almost all app objects plus the CEF wrapper. Several other test targets independently compile overlapping source lists. [Object rules](/Users/yn/work/talaria/.worktrees/refactoring-research/Makefile:161), [feature test linkage](/Users/yn/work/talaria/.worktrees/refactoring-research/Makefile:399), [other whole-app test targets](/Users/yn/work/talaria/.worktrees/refactoring-research/Makefile:389)

Tests also expose architecture coupling: split/restore tests populate internal window fields through KVC and private test categories. Such tests cover valuable behavior, but many simple state or lifecycle checks currently depend on constructing a broad object graph. This makes safe extraction harder and allows the production module boundaries to remain implicit. [Restore setup](/Users/yn/work/talaria/.worktrees/refactoring-research/Tests/WorkspaceRestoreTests.m:87), [split setup](/Users/yn/work/talaria/.worktrees/refactoring-research/Tests/SplitWorkspaceTests.m:240)

First adopt compiler-generated dependency files and include them from Make. Remove blanket header prerequisites only after confirming actual transitive includes are captured. Keep explicit generated-resource and compile-configuration dependencies. Per-source dependency files are the established Make mechanism for automatically tracking these relationships. [GNU Make automatic prerequisites](https://www.gnu.org/s/make/manual/html_node/Automatic-Prerequisites.html)

Then define focused object/library groups: core models and prompt/turn/state logic; storage and repositories; native design-system views; Hermes client/VM infrastructure; Chromium integration; and application composition. Keep browser-specific components in a group that can depend on browser contracts, rather than forcing a circular dependency through a catch-all UI library. Split the existing UIComponents implementation by its current component responsibilities as needed for those boundaries. Its 3,754 lines contain 29 implementations; this is useful modularization when it removes unnecessary dependencies, not simply a file-size target. [Component umbrella](/Users/yn/work/talaria/.worktrees/refactoring-research/Source/design_system/UIComponents.m:283)

Give each extracted controller/repository/transport its own test target with injected dependencies. Keep a smaller set of complete-window and real CEF integration targets for behaviors requiring the full stack. A change to a pure transcript diff or JSON frame decoder should be testable without building Chromium integration. Introduce a declarative Make helper for repeated test compile/link recipes; there is no demonstrated need to replace Make or move to a new project generator.

Deliver dependency tracking first because it benefits every later edit. Add module groups as the first four proposals create meaningful boundaries, and move tests alongside those extractions. Keep make test as the full correctness entry point, including the theme and no-direct-HTTP audits required by specs.

Validate a clean build, a no-op rebuild, a leaf-header edit, a widely shared header edit, a generated-resource change, and a relevant compiler-option change. Count rebuilt objects and linked test targets. Confirm the full suite still runs every existing test. Dependency omissions can produce stale successful binaries, so accurate rebuild behavior matters as much as shorter iteration time.

**Recommended execution sequence**

Start with three bounded changes that do not depend on the larger controller extraction: accurate build dependencies; transcript identity-membership/constraint lookup improvements; and a regression-backed session exclusion fix. Summary-only batched history imports are another independent early change.

Next establish per-chat controller ownership and serial repository ownership. Complete targeted rendering and history pagination behind those interfaces. Typed transport can proceed independently of the controller and repository extractions. Defer transcript virtualization and broad DOM diffing until profiling shows their remaining benefit. This ordering produces useful improvements early while reducing risk for the larger moves.

The five proposals preserve the existing specifications: Hermes TUI remains the sole AI interface, prompt generation stays in TLPromptBuilder, supporting-model work stays isolated, reusable controls live in design_system and consume existing semantic tokens, theme changes reach retained views, and the main window retains its 200 px minimum with no maximum width. They require no spec or README edits. [Project specifications](/Users/yn/work/talaria/.worktrees/refactoring-research/specs/hermes-tui-gateway.md), [prompting](/Users/yn/work/talaria/.worktrees/refactoring-research/specs/prompting.md), [components](/Users/yn/work/talaria/.worktrees/refactoring-research/specs/design-system-components.md), [theme](/Users/yn/work/talaria/.worktrees/refactoring-research/specs/theme-system.md), [window behavior](/Users/yn/work/talaria/.worktrees/refactoring-research/specs/window-behavior.md)

**Validation and limits**

The baseline validation completed successfully:

- 90 Python tests through make test-hermes-gateway, plus the theme-color audit.
- 13 AgentRuntimeTests and 7 TerminalServiceTests.
- Native AssistantTurnResultTests, AppStateManagerTests, WorkspaceSessionTests, and CredentialStoreTests, compiled and run from this worktree.
- A deterministic fake-RPC session lifecycle probe, reproducing the interleaving described above.
- Synthetic SQLite query-plan inspection using the relevant schema and existing indexes; the portable [query-plan probe](/Users/yn/work/talaria/.worktrees/refactoring-research/docs/research/query-plan-probe.py) reproduces the access paths without reading app data.

The terminal suite required building its native probe and permitting its temporary Unix-domain socket; it passed afterward. The native GUI/CEF suite and the complete make test target were not run. No desktop latency or memory profile was captured. Test success is baseline evidence, not proof that the proposed refactors are correct or that the whole application is currently defect-free.
